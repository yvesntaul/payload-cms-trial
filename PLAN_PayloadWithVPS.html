1. Project Context and Goals

1.1 Project Overview

ARtifacts is a cultural heritage platform developed in collaboration with the Pasig City Museum, housed within the historic Concepcion Mansion (built 1937, declared an Important Cultural Property in 2018). The platform consists of three interfaces:

  1. Mobile AR Application (Unity + ARCore for Android)
  2. Content Management System (Payload CMS)
  3. Public Showcase Website (Next.js)

1.2 Project Needs

  • Build the system before the deadline
  • Demonstrate that it works
  • Test it with real museum users
  • Train museum staff
  • Document everything
  • Hand over the system successfully
  • Make it possible for another developer to maintain later

1.3 Priority Order

Priority Focus Rationale
1. Development Speed Don't build what Payload already provides You have a deadline
2. Reliability Prefer mature, boring technologies Simplicity prevents failure
3. Accessibility Open-source with usable free tiers Cost-effective for museum
4. Maintainability Future developers should understand the system Handover matters
5. Portability Museum should not be trapped in one provider Institutional freedom
6. Cost Little or no recurring infrastructure cost Museum budget constraints
7. Scalability Design reasonably well, but don't over-solve Focus on what matters now

2.2 Mobile Application Responsibilities

The mobile app handles:

  • AR functionality (plane detection, tracking, rendering)
  • Artifact recognition and interaction
  • 3D model rendering with rotation/scale
  • Audio narration playback
  • Puzzle gameplay with timer and fragments
  • Difficulty management (Easy/Medium/Hard)
  • Pearl rewards and achievements display
  • Assessments (pre and post)
  • Visitor progress tracking
  • Local caching of assets
  • User authentication and session management

2.3 Critical Design Rule

The mobile application must NOT contain authoritative museum content.

Unity → Express API → Payload API → Artifact content

Never hard-code in Unity:

  • Artifact name, description, or historical period
  • Audio URLs or 3D model URLs
  • Puzzle difficulty parameters
  • Assessment questions or answers

This allows museum staff to update content without rebuilding the application.

Payload is a particularly good fit because:

5. Content Models

5.1 Artifacts Collection

Artifacts
├── name: string (required)
├── slug: string (auto-generated from name)
├── short_description: string
├── full_description: rich text
├── historical_period: string
├── date_or_time_period: string
├── origin: string
├── cultural_significance: rich text
├── thumbnail: Media (image)
├── model_file: Media (GLB/glTF)
├── audio_narration: Media (MP3/AAC)
├── _status: 'draft' | 'published' (Payload native)
├── workflowStatus: 'draft' | 'submitted' | 'approved' | 'rejected' | 'archived'
├── published_at: datetime
├── assessment_question: string
├── assessment_options: array of { text: string; is_correct: boolean }
├── difficulty_config: {
│   easy: { fragmentCount: number; timeLimit: number; pearlReward: number }
│   medium: { fragmentCount: number; timeLimit: number; pearlReward: number }
│   hard: { fragmentCount: number; timeLimit: number; pearlReward: number }
│ }
└── model_metadata: {
    fileSize: number
    polygonCount: number
    textureResolution: string
    mobileOptimized: boolean
    scale: number
    version: number
}

5.2 Critical Design Note

Use Payload's native _status field for draft/published control, plus a separate workflowStatus field for the editorial process:

Payload _status: draft / published
workflowStatus: draft → submitted → approved → rejected → archived

Do not replace Payload's native publishing system with a custom status field.

5.3 Exhibits Collection

Exhibits
├── name: string
├── slug: string
├── description: rich text
├── thumbnail: Media (image)
├── historical_period: string
├── artifacts: Relationship (many-to-many with Artifacts)
├── _status: 'draft' | 'published' (Payload native)
├── workflowStatus: 'draft' | 'submitted' | 'approved' | 'rejected' | 'published' | 'archived'
└── sort_order: number

5.4 Achievements Collection

Achievements
├── name: string
├── description: string
├── icon: Media (image)
├── requirementType: 'pearls_collected' | 'exhibits_completed' | 'perfect_score' | 'puzzles_completed'
└── requirementValue: number

5.5 Report Ownership Resolution

Final Decision: Reports are owned by Express.

Mobile App → Express (creates report) → PostgreSQL (stores report)
Payload → Read-only view of reports (via API integration or direct query)

Rationale: Reports are user-generated application activity, which belongs in Express. Payload may display reports to museum staff through an integration, but Express maintains the authoritative data.

6.5 API Security

Critical Rule: Don't put secret API keys inside the Unity APK.

Type Access Endpoints
Public No authentication Published artifacts, exhibits, achievements
Authenticated Valid JWT required User profile, game sessions, puzzles, assessments
Admin-Only Express admin role Analytics endpoints

For public museum content, use Payload's published-only access rules. Keep authentication, gameplay changes, rewards, and user data behind the Express API.

7. Database Architecture

7.1 Database Ownership Separation

Final Decision: Use separate PostgreSQL schemas with distinct database users.

PostgreSQL
    │
    ├── Schema: museum_content (owned by payload_user)
    │   ├── artifacts
    │   ├── exhibits
    │   ├── media
    │   └── achievements
    │
    └── Schema: application_data (owned by express_user)
        ├── users
        ├── sessions
        ├── game_sessions
        ├── puzzle_attempts
        ├── pearl_transactions
        ├── user_progress
        ├── assessment_attempts
        ├── events
        ├── achievements_earned
        ├── personal_bests
        └── reports

7.2 Implementation

-- Create schemas and users
CREATE SCHEMA museum_content;
CREATE SCHEMA application_data;

CREATE USER payload_user WITH PASSWORD 'secure_password';
CREATE USER express_user WITH PASSWORD 'secure_password';

-- Grant permissions
GRANT ALL ON SCHEMA museum_content TO payload_user;
GRANT ALL ON SCHEMA application_data TO express_user;

-- Payload can only read from application_data (for analytics display)
GRANT SELECT ON ALL TABLES IN SCHEMA application_data TO payload_user;

-- Express can only read from museum_content (for published content)
GRANT SELECT ON museum_content.artifacts TO express_user;
GRANT SELECT ON museum_content.exhibits TO express_user;
GRANT SELECT ON museum_content.achievements TO express_user;
GRANT SELECT ON museum_content.media TO express_user;

7.3 Critical Rule

Express should never directly modify Payload's internal tables. If Express needs artifact information, use the Payload API.

This makes future migration much easier.

7.5 Database Constraints

Use database constraints for important rules:

-- Prevent duplicate rewards
CREATE UNIQUE INDEX idx_unique_reward 
ON pearl_transactions (user_id, artifact_id, difficulty);

-- Ensure unique authentication tokens
CREATE UNIQUE INDEX idx_unique_session 
ON sessions (token_hash);

-- Prevent duplicate achievement unlocks
CREATE UNIQUE INDEX idx_unique_achievement 
ON achievements_earned (user_id, achievement_id);

-- Enforce valid status values
ALTER TABLE game_sessions 
ADD CONSTRAINT valid_status 
CHECK (status IN ('active', 'paused', 'completed', 'abandoned'));

9. Media and 3D Asset Stack

9.1 Storage Architecture

Area Recommended Choice

Delivery Cloudflare CDN
3D format GLB/glTF
Images WebP or optimized JPEG
Audio MP3 or AAC
Upload management Payload Media Library connected to R2

9.2 Storage Structure

models/
  artifact-001/v1/artifact-001.glb
  artifact-001/v2/artifact-001.glb

images/
  artifact-001/thumbnail.webp
  artifact-001/preview.webp

audio/
  artifact-001/en/narration.mp3
  artifact-001/tl/narration.mp3

Critical: Do not place large 3D assets inside PostgreSQL. PostgreSQL contains file references and metadata; object storage contains the actual binary files.

9.3 Content Delivery Strategy

Unity → R2/CDN → Large 3D Assets → Local Cache (Unity Addressables)

Why this matters:

  • Museums may have weak Wi-Fi
  • Inconsistent cellular signal
  • Many visitors simultaneously using the app

12. Data Migration: Strapi → Payload

12.1 Migration Strategy

Strapi Cloud → Export Data → Transform → Import → Verify → Production

12.2 Migration Steps

Step Action Details
1 Export Strapi data Use Strapi export plugin or manual export to JSON
2 Export media files Download all media from Strapi Media Library
3 Transform to Payload format Custom Node.js script maps fields
4 Upload media to R2 Use R2 console or AWS CLI
5 Register media in Payload Create Media records for each file
6 Import content to Payload Use Payload REST API or custom script
7 Verify relationships Check artifact-exhibit links
8 Test API endpoints Verify content accessible via API
9 Deploy to production Docker Compose with migrated data

12.3 Import Script Requirements

The migration script must:

  • Validate input data
  • Upload or register Media records in Payload
  • Preserve artifact-exhibit relationships
  • Handle duplicate records safely
  • Verify imported content
  • Produce an import report

12.4 Sample Migration Script

// scripts/migrate-strapi-to-payload.ts
import fs from 'fs';
import { Payload } from 'payload';

async function migrate() {
  // 1. Read Strapi export
  const strapiData = JSON.parse(fs.readFileSync('strapi-export.json', 'utf-8'));
  
  // 2. Initialize Payload client
  const payload = await Payload.init({
    secret: process.env.PAYLOAD_SECRET,
    local: true,
  });
  
  // 3. Transform and import each artifact
  for (const artifact of strapiData.artifacts) {
    // Validate data
    if (!artifact.name || !artifact.slug) {
      console.warn(`Skipping artifact ${artifact.id}: missing required fields`);
      continue;
    }
    
    // Upload media to R2
    const mediaId = await uploadMediaToPayload(artifact.model_file);
    
    // Create artifact in Payload
    const created = await payload.create({
      collection: 'artifacts',
      data: {
        name: artifact.name,
        slug: artifact.slug,
        short_description: artifact.short_description,
        full_description: artifact.full_description,
        historical_period: artifact.historical_period,
        // ... map all fields
        model_file: mediaId,
        _status: artifact.published ? 'published' : 'draft',
        workflowStatus: artifact.status || 'draft',
      },
    });
    
    console.log(`✅ Imported artifact: ${created.name}`);
  }
  
  // 4. Generate import report
  console.log('Migration complete!');
}

migrate().catch(console.error);

Note: The actual Payload import API may vary. Check the installed Payload version for the correct import method.

13. Backup and Recovery

13.1 PostgreSQL Backups

# Daily backup script
#!/bin/bash
BACKUP_DIR="/backups/postgres"
DATE=$(date +%Y%m%d_%H%M%S)
FILENAME="artifacts_$DATE.sql"

pg_dump -U artifacts -d artifacts > "$BACKUP_DIR/$FILENAME"

# Compress
gzip "$BACKUP_DIR/$FILENAME"

# Upload to off-server location
rclone copy "$BACKUP_DIR/$FILENAME.gz" remote:backups/

# Keep last 30 days
find "$BACKUP_DIR" -name "*.sql.gz" -mtime +30 -delete

13.2 R2 Backup Strategy

  • Enable R2 versioning (keeps history of all file versions)
  • Consider cross-region replication for critical assets
  • Document recovery procedures

13.3 Recovery Procedures

## Recovery Procedures

### PostgreSQL Recovery
1. Stop Payload and Express services
2. Restore database from latest backup
3. Start services

### R2 Recovery
1. If a file is deleted, restore from version history
2. If bucket is lost, restore from backup location

### Full System Recovery
1. Provision new VPS
2. Clone repository
3. Set up environment variables
4. Restore PostgreSQL from latest backup
5. Restore R2 files
6. Start services

13.4 Backup Requirements

Item Requirement
PostgreSQL Daily automated backup, 30-day retention
Off-server location Copy backups to separate location
Restore testing Test restore procedure quarterly
R2 media Use versioning or separate backup
Recovery procedures Document for Payload, Express, PostgreSQL, R2

19. Academic Defense

19.1 Architecture Explanation

┌─────────────────────────────────────────────────────────┐
│  Separation of Concerns                               │
├─────────────────────────────────────────────────────────┤
│  Presentation Layer                                   │
│  ├── Unity (Mobile AR)                               │
│  ├── Next.js (Public Website)                        │
│  └── Payload Admin (CMS Interface)                   │
├─────────────────────────────────────────────────────────┤
│  Application Layer                                    │
│  ├── Express API (Game/User Logic)                   │
│  └── Payload API (Content)                           │
├─────────────────────────────────────────────────────────┤
│  Data Layer                                           │
│  ├── PostgreSQL (Structured Data)                    │
│  └── Cloudflare R2 (Large Media)                     │
└─────────────────────────────────────────────────────────┘

19.2 Why This Architecture

  1. Separation of concerns — Each layer has a single responsibility
  2. Open-source first — All core components are MIT-licensed
  3. Portable — No vendor lock-in; works on any hosting
  4. Cost-effective — Free tiers for the initial deployment
  5. Maintainable — Standard technologies; easy for future developers
  6. Handover-ready — Documentation is a first-class requirement

19.3 Project Goal

"Develop an open, maintainable, and cost-efficient three-interface cultural heritage platform consisting of an Android AR application, a customized content management and analytics system, and a public showcase website, with a focus on institutional usability, content portability, and sustainable handover."
